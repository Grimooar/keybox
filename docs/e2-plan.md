# Э2: доступ Директора к Ключнице

Источник: план отделов Директора, §7.5, §8.9, §8.21 «Безопасность». Цель: Директор (программа владельца) получает доступ к Ключнице как отдельный участник, сам создаёт записи и отдаёт пароли своим скриптам, не видя их. Шифрование не ослабляется: сервер по-прежнему видит только шифртекст.

## Что уже есть и что мешает

- Участник работает без мастер-пароля: сервер проверяет подпись запроса (`X-KB-Auth`) по `signPk` из файла команды, ключи коллекций запечатаны на `boxPk`. Для программы достаточно `uid`, `signSk`, `boxSk`, секрета команды и закрепа (`pin`).
- `accessOf()` ограничивает только `member`; коллекция `all: true` открыта всем участникам, значит и Директору.
- У любого участника есть личный сейф `p-<uid>` и право создавать отправки (`api/sends`): это обходы мимо коллекции «Директор».
- Журнала запросов на сервере нет.

## Решения

1. **Участник-сервис = `member` + флаг `service: true`** в записи участника в `org.json` (файл подписан владельцем/админом).
   - Роль остаётся `member`: старые проверки ролей (`requireAdmin`, `canReadVault`) работают как раньше, новой роли с широкими правами по ошибке не появится.
   - `accessOf()`: сервис не получает коллекции `all: true` (ни ключа, ни файла). `verifyOrg()` запрещает: флаг у не-`member`, флаг не `true`, ключ коллекции `all: true`, запечатанный для сервиса.
   - Сервер: сервису нельзя читать и писать личный сейф, создавать отправки, читать файлы других участников (даже публичную часть). Флаг «липкий»: снять его с участника нельзя, только удалить участника и принять нового.
   - Клиент: `approve(uid, code, cids, { service: true })`, `setRole()` не делает сервис админом, у сервиса нет «Личного» в списке коллекций. В окне заявки галочка «Участник-сервис» (включена, если заявка помечена `kind: 'service'` при `kb enroll`).
2. **Журнал `audit` на сервере** (`schema.sql`): время, uid, метод, класс пути (`api/f/vault/*`), объект (cid коллекции или uid файла участника), статус, HMAC адреса. Без тел запросов, заголовков, параметров, id отправок и текстов ошибок.
   - Пишется для каждого запроса, кроме OPTIONS и `api/status`; ошибка записи журнала (например, таблицы ещё нет) запрос не ломает.
   - HMAC адреса - только ключом `AUDIT_SALT` из секретов Workers; без него адрес не пишется (перец из той же D1 не годится: по дампу IPv4 перебирается). Строки - только запросам с верным секретом команды на известный путь, остальное - счётчик `audit_denied`; потолок строк `AUDIT_MAX_ROWS`. uid - только после проверки подписи или пароля.
   - Хранится `AUDIT_DAYS` (по умолчанию 180) дней, старое удаляется попутно.
   - `GET api/audit?since=&limit=`: владелец и админы видят всё, участник - только свои строки (Директор сверяет свой журнал `kb_audit.jsonl`).
3. **CLI `kb`** (`cli/kb.mjs`, Node 20+, без зависимостей): переиспользует `js/crypto.js`, `js/vault.js`, `js/storage.js`, `js/tools.js` из этого же коммита.
   - Ключи - только из переменных окружения (их подставляет `vault.py run kb_* -- kb ...`): `KB_API`, `KB_UID`, `KB_SIGN_SK`, `KB_BOX_SK`, `KB_TEAM_SECRET`, `KB_PIN`. Публичные ключи CLI выводит из секретных. Мастер-пароль для работы не нужен.
   - Команды: `enroll`, `list`, `create`, `run`, `rotate`, `totp`, `selfcheck`, `audit`, `scan`.
   - Значения секретов не выводятся никогда: ни в stdout, ни в stderr, ни в ошибках. `run`/`totp` кладут значение только в env дочернего процесса и возвращают его код выхода. Команды «показать значение» нет, отправок и личного сейфа тоже.
   - `scan ФАЙЛ...` - ночная проверка «0 значений в журналах»: расшифровывает пароли видимых записей в памяти и сообщает только имена записей, чьи значения нашлись в файлах (вместо HMAC-отпечатков из §7.5: точнее и не требует отдельного ключа).
   - Состояние против отката (`seen`: версии файла команды и коллекций) - в `KB_STATE_DIR` (по умолчанию `~/.keybox-cli`), без секретов.
4. **Тесты** (`tests/cli.test.mjs` + дополнения в `core`/`server`): полный путь enroll -> одобрение -> create/list/run/rotate/totp/selfcheck на настоящем обработчике сервера; запреты для сервиса; журнал; и отдельно - секрет не попадает в stdout/stderr CLI, в `console.*` сервера и в строки `audit`.

## Шаги (коммит после каждого)

1. План (этот файл).
2. Участник-сервис: `vault.js` + сервер + тесты.
3. Журнал `audit`: схема, запись, `GET api/audit`, тесты.
4. CLI `kb` + тесты.
5. Приложение: галочка в заявке, метка «сервис», `CACHE` в `sw.js`; README.

## Что делает владелец (после «да», не в этой ветке)

1. Ревью ветки `feat/e2-director-access`, слияние в `main`.
2. Миграция боевой D1: `cd server && npx wrangler d1 execute <база> --remote --file=schema.sql` (только `CREATE ... IF NOT EXISTS`, существующие таблицы не трогает).
3. Деплой воркера: секрет `AUDIT_SALT` (`openssl rand -hex 32 | npx wrangler secret put AUDIT_SALT`, без него адрес в журнал не пишется), затем `npx wrangler deploy`.
4. Публикация PWA (GitHub Pages) и пересборка расширения (2.3.0). Старые клиенты требуют ключ коллекции «для всех» для каждого участника, поэтому сервер и приложение не принимают сервис, пока есть коллекции «для всех», и не создают их при сервисе в команде: до принятия Директора сделать все коллекции «для всех» «для выбранных» (§7.5).
5. Подключение Директора: в приложении создать приглашение, на ПК Директора `kb enroll --link '<ссылка с #t=..&c=..&i=..>' --name Директор --out <файл>`; сверить код участника, принять заявку с галочкой «Участник-сервис»; создать коллекцию «Директор» (не «для всех») только с ним; перенести файл с ключами в S1 (`vault.py`) и удалить его; `kb selfcheck`.

## Не входит в Э2

`core/keybox.py`, хуки и `permissions.deny` в Директоре, ночная сверка `kb_audit.jsonl` с сервером и тревога О14 - это сторона Директора (command-center).
